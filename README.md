# TurnVK

Клиент для серверов WDTT: WireGuard через TURN-серверы звонков VK. С сервером TurnVK в [wdtt-router](https://github.com/Jetvac/wdtt-router) работает по собственному прямому протоколу, со стандартным сервером WDTT — по обычному (DTLS + GETCONF). Принимает те же ссылки `wdtt://`.

Платформы: Android (приложение) и Windows (приложение с окном и VPN для всего компьютера; есть и консольный клиент с SOCKS5-прокси). Ядро одно на все платформы, оформление приложений одинаковое.

## Как это работает

```
приложение ─► WireGuard (в процессе) ─► маршруты ─► TURN VK ─► сервер WDTT ─► интернет
                                          │
                                          └─ каждый маршрут: UDP-сокет → выделение на TURN VK →
                                             RTP-маскировка (ChaCha20-Poly1305) → HELLO (прямой протокол)
                                                                               или DTLS 1.2 → GETCONF (стандартный)
```

1. По ссылке звонка VK клиент заходит в звонок анонимным гостем (как веб-клиент VK Звонков) и получает учётные данные TURN.
2. Открывает несколько маршрутов, каждый — через своё выделение (allocation) на TURN-сервере VK. Весь трафик идёт только через TURN VK, напрямую к серверу клиент не подключается.
3. WireGuard работает внутри процесса и передаёт пакеты прямо в маршруты, без локального UDP-порта.

## Прямой протокол (сервер TurnVK)

Стандартный протокол открывает на каждом выделении отдельное DTLS-соединение и повторяет на нём GETCONF; пропало выделение — пропало соединение, перезапустился сервер — рвутся все. Прямой протокол убирает DTLS:

- **Соединение — это сама сессия WireGuard**, сквозная между клиентом и сервером. Маршруты через TURN VK к ней только подключаются: одно сообщение HELLO, один ответ WELCOME. Маршрут можно потерять или добавить без рукопожатия.
- **Шифрование в два слоя.** Внутри — WireGuard (Curve25519, ChaCha20-Poly1305, прямая секретность). Снаружи — RTP-маскировка под аудио или видео звонка, тоже ChaCha20-Poly1305 по ключу из пароля. Без пароля сервер не отвечает вообще, порт выглядит закрытым.
- **Ключ WireGuard клиент создаёт сам** при каждом подключении и отправляет серверу только открытую часть. Сервер больше не выдаёт закрытых ключей, и даже знающий пароль не прочитает чужой трафик.
- **Ключ сервера в ссылке** (`?pk=…`, панель добавляет его в ссылки TurnVK). Клиент сверяет его и не подключится к подменённому серверу, даже если у подменившего есть пароль. Без `?pk=` клиент сам определяет, понимает ли сервер прямой протокол, и иначе переходит на стандартный.
- **Живость каждого маршрута.** Каждые 4 с — PING с замером задержки. Клиент и сервер шлют трафик только по отвечающим маршрутам. Когда туннель замолкает, клиент проверяет маршруты и заменяет только умершие, остальные продолжают работать. Закрывая маршрут, клиент сообщает об этом серверу (BYE).
- **Обратный трафик по всем маршрутам.** Сервер распределяет ответы устройству по всем его живым маршрутам, а не только по последнему.
- **Перезапуск сервера** стоит одного HELLO на маршрут: сервер отвечает RESET на пакет неизвестного маршрута, клиент тут же подключает его снова и обновляет ключи WireGuard.
- **Защита от повтора HELLO** (метка времени и одноразовое число). Если часы устройства сбиты, сервер сообщает своё время, и клиент поправляется сам.
- Новое подключение того же устройства (перезапуск приложения) сразу забирает адрес; маршруты прежнего запуска сервер закрывает.

## Чем отличается от исходного клиента

| | Исходный клиент | TurnVK |
| --- | --- | --- |
| Путь пакета | WireGuard-приложение → UDP 127.0.0.1:9000 → отдельный процесс клиента → сессии | WireGuard и сессии в одном процессе, без локального сокета и лишних копий |
| Распределение по сессиям | по 12 пакетов на сессию по кругу | каждый пакет — в тот маршрут, где он дойдёт раньше (учитывается, сколько уже отправлено в маршрут, и время прохождения); короткие пакеты не ждут за загрузкой. Сервер TurnVK к тому же ведёт каждый маршрут с той скоростью, которую VK пропускает без потерь (см. «Скорость и задержка») |
| Перезапуск сервера | клиент ждёт до 30 минут (таймаут чтения) или 90 с до перезапуска сторожем; потом ещё ~16 с на рукопожатие WireGuard | закрытие сессий сервером замечается сразу, сброс устаревшей сессии — по первому пакету; рукопожатие WireGuard — сразу, без ожидания таймаута |
| Сервер замолчал без сброса | — | переподключение через 8 с, если пакеты уходят, а ответа нет; с сервером TurnVK — проверка маршрутов через 2 с и замена только умерших |
| Пропало одно выделение TURN | соединение на нём рвётся | с сервером TurnVK трафик уходит на остальные маршруты, умерший заменяется |
| Ключи | сервер присылает закрытый ключ WireGuard | с сервером TurnVK ключ создаётся на устройстве, ключ сервера сверяется со ссылкой |
| Смена сети (Wi-Fi ↔ LTE) | ждёт, пока сессии отвалятся | сессии переоткрываются сразу |
| Учётные данные VK | группа из 9 сессий на набор, новый гость на каждый запрос | группа из 8 сессий на набор, до 16 сессий на гостя звонка (больше VK не даёт: ошибка 486); учётные данные обновляются раз в час, а не каждые 8 минут, и сохраняются между запусками — перезапуск в пределах часа обходится без запросов к VK |
| Капча VK | автоматический обход (подделка отпечатка браузера, решение головоломки, автонажатие) | капча показывается пользователю, на Android — с уведомлением; после проверки подключение продолжается само. Гостевые токены VK живут сутки и сохраняются на устройстве, поэтому капча бывает не чаще раза в сутки на звонок, а не при каждом обновлении учётных данных и перезапуске |
| MTU | не ниже 1280, даже если сервер прислал меньше | берётся из конфигурации сервера |

## Замеры

Windows, домашний интернет, реальные TURN-серверы VK, тестовый сервер wdtt-router (1 vCPU), выход через второй сервер:

- подключение — 1,2–1,5 с, первый запрос — около 0,2 с;
- скачивание 50 МБ: 16 сессий — 23,6 Мбит/с, 24 сессии — 31,0 Мбит/с;
- плановый перезапуск сервера — теряется один запрос, который был в пути; аварийное завершение сервера (SIGKILL) — туннель восстанавливается примерно через 2 с после запуска сервера.

Прямой протокол, 14.11.2026: тестовый сервер TurnVK в Германии, 4 маршрута, запрос раз в секунду:

- подключение — 1,3–1,8 с;
- перезапуск сервера посреди работы — 40–42 запроса из 41–42 прошли;
- один маршрут перестал пропускать пакеты (заблокирован на сервере) — 85 из 86 запросов прошли, маршрут заменён сам; на стандартном протоколе тот же сбой давал каскад переподключений;
- скачивание через 8 маршрутов — 11–13 Мбит/с (стандартный протокол в те же минуты — 9–11 Мбит/с; предел задают TURN-серверы VK).

## Скорость и задержка

VK ограничивает каждое выделение TURN примерно 1,5–2 Мбит/с, и ограничивает жёстко: всё, что пришло сверх нормы пачкой, отбрасывается почти целиком, пока запас не восстановится. Загрузка без управления идёт рывками — секунда на 60 Мбит/с, секунда с потерей 90 % пакетов. TCP после таких потерь замирает, пинги теряются или ждут. Поэтому:

- сервер TurnVK отправляет в каждый маршрут ровно с той скоростью, которую VK пропускает: очередь копится на сервере, а не теряется у VK;
- в этой очереди короткие пакеты (пинг, подтверждения TCP, DNS, игры, звонки) идут первыми, а крупные, ждущие дольше 60 мс, сбрасываются — TCP замедляется раньше, чем вырастет задержка;
- получатель, пока идут данные, до 20 раз в секунду сообщает по каждому маршруту (FEEDBACK): номер последнего пакета, сколько он ждал отправки отчёта, сколько пакетов дошло и сколько потеряно. Отправитель помнит, когда отправил этот пакет, и получает задержку самих данных. Раз в 100 мс скорость маршрута меняется: при потерях больше 5 % (на сотню пакетов) — на 15 % ниже, при росте задержки на 25 мс над обычной — на 8 % ниже (но из-за одной задержки не ниже половины начальной скорости), пока маршрут чист, быстр и занят — на 2 % выше. Случайные потери мобильной сети в пару процентов скорость не снижают — снижают только выбросы ограничителя VK;
- так же работает и отдача: клиент ведёт маршруты по отчётам сервера. Крупные пакеты отдачи идут по одному маршруту, пока его запас не кончится: TCP-отправитель здесь — само устройство, и многие стеки (в консольном клиенте, старые Windows и Android) принимают переупорядочивание за потери и замедляются (замер: вдвое быстрее, чем при сериях по 4 пакета);
- самые короткие пакеты (до 256 байт: подтверждения TCP, DNS, пинг) идут сразу по двум маршрутам: какой дойдёт первым, тот и считается, второй WireGuard отбрасывает как повтор;
- пакеты, пришедшие по разным маршрутам не по порядку, выстраиваются по номеру пакета WireGuard (он виден без расшифровки), прежде чем их увидит WireGuard: пакет, пришедший раньше, ждёт предыдущие не дольше 10 мс (`core/engine/reorder.go`, у сервера — та же копия). Опоздавшие и повторы проходят сразу;
- новый маршрут начинает со скорости, на которой недавно держались маршруты через тот же TURN-сервер, и до первых признаков перегрузки разгоняется быстрее (+8 % за 100 мс, потом +2 %);
- с сервером без отчётов (стандартный, прежний TurnVK) клиент отправляет как раньше, без управления скоростью; прежние клиенты TurnVK получают управление по отчётам в PING раз в 2 с.

Отказ маршрутов и плохие TURN-серверы VK:

- каждый пинг маршрута (раз в 2 с) — ещё и проверка: маршрут, не ответивший за 2 с, перестаёт получать трафик, пока не ответит (раньше — через 10 с молчания). Маршрут, молчащий 6 с, пока другие отвечают, заменяется новым (раньше — через 25 с), а замена маршрута, проработавшего больше минуты, открывается сразу, без паузы — если только не упало сразу много маршрутов (смена сети, перезапуск сервера): тогда новые выделения растягиваются во времени, как раньше;
- сервер TurnVK перестаёт слать в маршрут, если клиент не подтвердил отправленное за 0,75 с (клиент TurnVK подтверждает каждый пакет отчётом FEEDBACK), и снова шлёт, как только по маршруту что-то пришло;
- VK выдаёт на звонок несколько TURN-серверов, и они неравноценны: в замере с тестового сервера через один терялось 2–14 % пакетов сервера, через другой — 0–1 %, и первый пропускал в 3–5 раз меньше. Клиент считает потери по каждому TURN-серверу (окна по 10 с, не меньше 300 пакетов) и, если один заметно хуже лучшего (потери больше 3 % и больше чем вдвое), новые маршруты открывает на лучшем, а с плохого переводит по одному маршруту (с 0.8.2 — не чаще раза в 30 с); два остаются на нём, чтобы его продолжать мерить. Когда потери у серверов равны, ничего не меняется. С 0.8.2: если теряет больше 2 % даже лучший сервер, теряет сама сеть устройства (мобильная), и по потерям маршруты не переводятся — в статистике телефон в мобильной сети переводил маршрут каждые 10–30 с при потерях 3–28 % у всех серверов, и каждый перевод стоил нового выделения у VK. Зато хуже считается и сервер, отвечающий намного медленнее лучшего (задержка больше двойной лучшей плюс 50 мс): после переподключения маршруты иногда встают на сервер с задержкой 500–800 мс вместо 40. Пока VK отказывает в выделениях (ошибка 486) и пока телефон дремлет, маршруты не переводятся вовсе (`core/engine/relays.go`);
- закрывая маршрут, клиент освобождает его выделение TURN и дожидается ответа VK (при устаревшем nonce — повторяет с новым), (до 5 с на ответ — с 0.8.2, в медленной мобильной сети 2 с не хватало), а при отключении ждёт этого до 3 с: выделение, которое VK продолжает считать, при быстром перезапуске упирается в лимит (ошибка 486) и уводит маршруты на нового гостя VK, а это может стоить капчи. Библиотека pion отправляет освобождение один раз без ожидания. На тестовом сервере VK подтвердил освобождение всех 16 выделений в каждом прогоне; ошибки 486 в замерах появлялись только после проверок с заблокированным TURN-сервером, когда освобождение до VK не доходило. Не освобождённые выделения клиент пишет в журнал;
- если новый маршрут через TURN-сервер не открылся, или все маршруты через него разом замолчали, новые маршруты минуту обходят этот сервер; маршрут, который не открылся, пробует следующий сервер. Раньше каждый маршрут всегда шёл на один и тот же сервер, и если тот переставал отвечать, половина маршрутов не восстанавливалась до перезапуска. С 0.8.3 сервер считается замолчавшим, только если маршруты через другие серверы отвечали хотя бы на 2 с позже его последнего пакета: когда замолкает всё сразу (перезапуск сервера WDTT, пропала сеть), раньше клиент винил тот TURN-сервер, чьи маршруты замолчали первыми, и закрывал их — половину маршрутов, которые потом снова выделялись у VK. Теперь маршруты опрашиваются, а не закрываются. Число маршрутов в окне не показывается больше заданного («26 из 24»): маршруты, открытые до ошибки 486, продолжают работать.

Файлы `core/session/pace.go` и `core/engine/reorder.go` общие с сервером (`internal/wdtt/pace.go` и `internal/wdtt/reorder.go` в wdtt-router): копии должны совпадать.

Упорядочивание и быстрый старт 15.11 не дали заметной разницы в замерах: в тот час домашняя сеть была перегружена (замеры на 32 маршрутах — 12–24 Мбит/с у обеих версий), и разница тонула в шуме. Хуже ни в одном прогоне не стало.

Проверка на Android 14 (эмулятор, настоящий движок, 32 маршрута, 15.11): подключение и все экраны работают; пинг сервера через туннель — 53–67 мс (в среднем 57) без потерь; отдача — около 20 Мбит/с, загрузка — 14–20 Мбит/с. Отдача на телефоне в 5–8 раз быстрее, чем у консольного клиента, — значит, медленная отдача консольного клиента — особенность его встроенного стека TCP (gVisor), а не туннеля.

Отказ TURN-сервера VK посреди загрузки 150 МБ (16 маршрутов, тестовый сервер, 15.11; сервер VK перестаёт пропускать пакеты на 30-й секунде):

| | прежний клиент | новый клиент |
| --- | --- | --- |
| сервер отвечает ошибкой | остаётся 8 маршрутов из 16 до конца; 9–11 Мбит/с в среднем | 16 из 16 через несколько секунд, все через исправный сервер; 14–20 Мбит/с |
| сервер молча перестаёт пропускать | 8 рабочих маршрутов из 16 до конца | замолчавшие заменены через 7 с, 16 из 16 через 9–12 с |

При молчаливом отказе загрузка у нового клиента на 5–6 с останавливается совсем (TCP отправителя ждёт повторов после потерь первых долей секунды), потом идёт на полной скорости; у прежнего — около 10 с на 2–8 Мбит/с, а дальше на половине маршрутов. За 20 с после отказа новый клиент получил примерно в 1,6 раза больше данных.

Стандартный сервер и стандартные клиенты работают как раньше.

### Сон устройства

Телефон в фоне засыпает: таймеры останавливаются, и после пробуждения все маршруты выглядят молчащими, пока не придёт ответ на следующий пинг. Раньше клиент принимал это за отказ маршрутов и заменял их десятками, а каждая замена — новое выделение TURN у VK; за несколько часов это упиралось в лимиты VK, и помогало только переподключение. Теперь клиент замечает сон (по скачку настенных часов между тиками), опрашивает маршруты и 15 секунд их не трогает, а 25-секундный таймаут маршрута считается от пробуждения. Если молчит больше четверти маршрутов сразу (и не все маршруты одного TURN-сервера), это сеть, а не маршруты: клиент их опрашивает, а не заменяет.

С 0.8.2: Android с выключенным экраном останавливает приложение на 4–6 секунд снова и снова (в статистике — сотни «сна» в час у одного телефона). Такие короткие паузы больше не вызывают опроса всех маршрутов и строки в журнале, а только откладывают замену маршрутов. После любого сна две минуты телефон считается дремлющим: молчащий маршрут заменяется через 20 с молчания вместо 6 (его пинги тоже стояли), а маршруты не переводятся между TURN-серверами. Опрос всех маршрутов — только после сна дольше 20 с.

**Лимит выделений VK (ошибка 486)**, с 0.8.2. Раньше группа маршрутов, которой VK отказал, переходила к следующему гостю звонка, а когда гости кончались, клиент на каждую ошибку запрашивал у VK новые учётные данные того же гостя — и снова получал 486: в статистике телефон с 64 маршрутами сделал так почти 300 запросов к VK за полтора часа. Теперь группа переходит к гостю, которого не использует другая группа и который не упирался в лимит последние 5 минут (выделения закрытых маршрутов за это время освобождаются); если такого нет, она оставляет свои учётные данные и ждёт минуту (затем 2, 4, до 5 минут), а клиент на время уменьшает число маршрутов на 8 (не меньше половины заданного) — в окне и в статистике видно «маршрутов нужно». Через 15 минут без ошибки 486 он снова пробует на 8 больше.

**Нет сети**, с 0.8.2. Когда сети нет совсем (`network is unreachable`), новые маршруты не открываются один за другим: раз в 15 с пробует один, остальные ждут его или сообщения системы о новой сети. Одинаковые строки журнала (отличающиеся только числами) пишутся не больше 3 раз в минуту, дальше — одна строка «и ещё N таких».

**Сервер не отвечает**, с 0.8.4. Если VK выделяет маршруты, но сервер WDTT не отвечает ни на одном (`no answer to HELLO`) — он выключен или у него пропала сеть, — новые маршруты не открываются все подряд: в статистике телефон за ночь, пока сервер был отключён, открывал у VK около 55 выделений в минуту больше часа. Теперь проверяет один маршрут: через 15 с, затем 30 с, 1 и 2 минуты; остальные ждут его. В журнале одна строка «the server does not answer: one route checks it every …».

**Гости после перезапуска**, с 0.8.4. Если приложение закрыли без сети или его остановила система (например, при обновлении), выделения маршрутов остаются у VK до конца срока (около 10 минут), и новое подключение с теми же гостями звонка сразу получает ошибку 486. Клиент запоминает в кэше VK, какие гости держали выделения, и первые 10 минут после такого перезапуска начинает с других гостей. При обычном отключении, когда все выделения освобождены, отметки стираются и гости остаются прежними.

**Возврат к числу маршрутов**, с 0.8.4. Если после 15 минут без ошибки 486 клиент пробует на 8 маршрутов больше и сразу снова получает 486, это число устройству не подходит: он сразу возвращается к меньшему, а следующую попытку делает через 30 минут, затем через 60.

**Быстрее замечает умерший маршрут**, с 0.8.4. Маршрут, по которому идут пакеты, но от сервера ничего не было больше секунды, сразу проверяется пингом, не дожидаясь очередного (раз в 2 с). Ответ ждётся несколько задержек маршрута (от 0,5 до 2 с), а не всегда 2 с. Пока ответа нет, пакеты идут по другим маршрутам: TCP теряет на умершем маршруте около 1,5 с вместо 4.

**Короткие пакеты — по самому быстрому маршруту**, с 0.8.4. При выборе маршрута для отдачи запас скорости маршрута весил больше, чем его задержка, и в простое пинг или подтверждение TCP могли уйти через более медленный TURN-сервер VK. Теперь маршрут оценивается как половина задержки плюс то, что уже ждёт в нём своей очереди. То же исправлено на сервере TurnVK (wdtt-router 1.5.3).

**Порядок пакетов**, с 0.8.4. Пакеты, пришедшие по разным маршрутам в один момент, иногда передавались WireGuard не по порядку, хотя буфер упорядочивания их уже выстроил. Теперь они уходят строго по порядку.

**Пинг через VPN**, с 0.8.5. На вкладке «Журнал» кнопка «Проверить пинг»: 20 секунд, 4 раза в секунду открывается соединение с 1.1.1.1 через туннель (при любых правилах раздельного туннелирования), и каждый замер — это полный путь, как у игры: VK, сервер и дальше. Показываются обычная задержка, 95 % замеров, худший, разброс, всплески (на 50 мс выше обычного) и потери, на Windows — по ходу замера. Итог пишется в журнал и в статистику для сервера.

**Статистика задержек**, с 0.8.5. В ежеминутной статистике для сервера появились распределения, а не только средние: время ответа маршрутов на пинги (медиана, 95 % и 99 % замеров, худшее, сколько дольше 100 мс), сколько ждали пакеты в буфере упорядочивания и короткие пакеты в очереди отдачи, сколько пакетов очередь отдачи сбросила как устаревшие, сколько полученных пакетов не успел принять WireGuard и сколько дыр в порядке пакетов так и не заполнилось (потери).

**Маршрут, который молчит в ответ**, с 0.8.5. Сервер TurnVK подтверждает каждый полученный пакет (FEEDBACK, не позже чем через 50 мс). Если на отправленное по маршруту за несколько его задержек (от 0,3 до 2 с) не пришло ничего, маршрут перестаёт получать пакеты, пока не ответит: с ~15 мс задержки это около 0,3 с вместо 1,5 с.

**Копии коротких пакетов через другой TURN-сервер VK**, с 0.8.5. Короткие пакеты, до 400 байт вместо 256 (почти все пакеты игр), уходят сразу по двум маршрутам, и второй теперь идёт через другой TURN-сервер VK, если он есть: если один TURN-сервер застрянет, копия пройдёт через другой. Так же делает сервер TurnVK с wdtt-router 1.5.4.

**Wi-Fi без энергосбережения** (Android), с 0.8.5. В режиме энергосбережения Wi-Fi телефон принимает пакеты пачками раз в 100–300 мс, и игры видят это как всплески пинга. Пока TurnVK подключён, приложение держит блокировки Wi-Fi: «низкая задержка» (Android 10+) действует, пока TurnVK на экране, «высокая производительность» — и в фоне, до Android 13 (с Android 14 система заменяет её на «низкую задержку», то есть в фоне это не действует).

**Короткие очереди, пока идёт игра или звонок**, с 0.8.6. Клиент и сервер TurnVK (wdtt-router 1.5.5) сами замечают интерактивный трафик — ровный поток коротких пакетов, от 20 в секунду, — и пока он идёт (и 5 секунд после), держат очереди короче. Скорость маршрута снижается уже при 10 мс очереди у VK вместо 25, после паузы маршрут отправляет сразу не больше 8 КБ вместо 24, а крупные пакеты, ждущие дольше 25 мс вместо 60, сбрасываются, чтобы TCP раньше замедлился. Загрузка рядом с игрой идёт немного медленнее, зато пинг в игре меньше скачет. В статистике для сервера — сколько секунд в минуту действовал этот режим (`low_lat`).

**Игры напрямую**, с 0.8.6. Переключатель на вкладке «Маршруты» работает при любом режиме, даже когда раздельное туннелирование выключено. На Windows мимо VPN идут найденные на компьютере лаунчеры (Steam, Epic Games, Riot, Battle.net, EA app, Ubisoft Connect, GOG Galaxy), все программы, которые они запускают, и папки с играми, включая все библиотеки Steam и игры Epic. На Android система не пускает в VPN приложения, которые магазин относит к играм. Сайты, которые правила отправляют через VPN, по-прежнему идут через VPN, а сайт, который не открылся напрямую, открывается через VPN. Свои правила для тех же программ важнее. Игру, которую TurnVK не нашёл, можно добавить правилом «напрямую».

**Экономия заряда на Android**, с 0.8.7. Когда через VPN полторы минуты почти ничего не идёт, приложение оставляет 4 маршрута вместо всех, и они проверяют связь все вместе раз в 25 секунд, а не каждый раз в 2 секунды. Радиомодуль телефона после каждого пакета ещё несколько секунд работает на полной мощности, поэтому десятки маршрутов, каждый со своими проверками и продлениями у VK, не давали ему уснуть совсем. Пакет, отправленный в простое (например, проверка связи мессенджера), заодно запускает проверку маршрутов, чтобы радио проснулось один раз, а не два. Отчёты статистики для сервера в простое уходят вместе с этими проверками. Как только трафик пошёл (две секунды подряд от 30 пакетов или 300 пакетов за секунду: игра, звонок, страница), все маршруты возвращаются, по несколько за раз, а 4 оставшихся тем временем везут трафик. В простое Wi-Fi работает в обычном режиме энергосбережения (с 0.8.5 он был выключен всё время подключения), а экраны приложения в фоне больше не опрашивают состояние каждую секунду. В уведомлении — «простой, экономия заряда», в статистике для сервера — секунды простоя в минуту (`quiet`). Сервер TurnVK с wdtt-router 1.5.6 в простое отправляет телефону данные через маршрут, который отвечал последним; со старым сервером тоже работает.

**Маршруты переживают сон телефона**, с 0.8.8. Библиотека TURN продлевает разрешения и выделения VK по таймерам, которые стоят, пока телефон спит, а VK отсчитывает время по настоящим часам. Ночью маршруты из-за этого пропадали один за другим, и приложение пересобирало их все (до 28 раз за ночь). Теперь после сна каждый маршрут сам продлевает своё выделение и разрешение, как только телефон ненадолго проснулся; маршрут, который VK уже забыл, сразу заменяется. Простой (экономия заряда) считается по настоящему времени, а короткая синхронизация приложений в окнах обслуживания Android проходит через 4 оставленных маршрута и не возвращает все.

**Пропала сеть — маршруты ждут**, с 0.8.8. Пока сети нет (лифт, туннель, Wi-Fi пропал на секунды), маршруты не закрываются: открыть новые всё равно нельзя, а старые VK не освободил бы и считал бы против лимита (ошибка 486 после возвращения сети). Когда та же сеть вернулась, маршруты проверяются, и заменяются только те, что не отвечают. При смене сети (слабый Wi-Fi → мобильная) на Android новые маршруты открываются, пока старые, привязанные к прежней сети, ещё везут трафик; старые закрываются, когда ответил первый новый.

**Выбор TURN-серверов и путей**, с 0.8.8. Каждый TURN-сервер, который выдал VK, сразу проверяется коротким STUN-запросом, и маршруты не открываются на сервере, отвечающем намного медленнее лучшего. Оценка потерь сервера, через который почти ничего не идёт, со временем устаревает и больше не уводит с него маршруты по одному. Короткие пакеты (игры, звонки) выбирают маршрут по пингу с учётом его разброса, а не по последнему замеру; сервер TurnVK с wdtt-router 1.5.7 делает так же в обратную сторону.

**Расход заряда в статистике**, с 0.8.8. В каждой минуте статистики для сервера — уровень заряда и оставшиеся мА·ч, ток, зарядка, экран, Doze и экономия заряда (`dev`), сколько раз телефон просыпался (`wakes`) и сколько процессорного времени ушло на приложение (`cpu_ms`). Время сна (`gap`) теперь считается по настоящим часам.

**Режимы энергосбережения** (Android), с 0.8.9. В настройках, в разделе «Энергосбережение», можно выбрать, как TurnVK ведёт себя без трафика. «Баланс» (по умолчанию) — как с 0.8.7: через 1,5 минуты простоя остаются 4 маршрута, Wi-Fi без энергосбережения только пока идёт трафик. «Экономия» — простой уже через 30 секунд, остаются 2 маршрута, Wi-Fi всегда в режиме энергосбережения: заряд держится дольше, но пинг в играх может прыгать. «Всегда на связи» — простоя нет, все маршруты всегда наготове, Wi-Fi без энергосбережения всё время подключения: нет задержки после простоя, но заряд уходит быстрее. На главном экране под раздельным туннелированием — строка с текущим режимом; в простое она становится зелёной и объясняет, что происходит. Режим применяется при следующем подключении. В статистике для сервера — выбранный режим (`power`), в диагностическом отчёте — тоже.

**Сбой отправки при запуске игр**, с 0.9.0. Когда запускается игра с античитом (в журналах — Fortnite с Easy Anti-Cheat), Windows на несколько секунд отказывает в отправке всем UDP-сокетам («the system lacked sufficient buffer space»). Раньше клиент считал маршруты умершими и закрывал все сразу, а освободить их у VK не мог — VK отвечал ошибкой 486, клиент перебирал гостей звонка и четверть часа работал на 24 маршрутах из 32. Теперь это считается коротким пропаданием сети: маршруты держатся, пока отправка не заработает, а запрос на освобождение маршрута у VK повторяется через 1, 3 и 10 секунд.

**Одна игра — один выход**, с 0.9.0 (Windows). UDP-сокет программы, которую её правило (в том числе «Игры напрямую») отправило напрямую, сохраняет этот маршрут для всех адресов, с которыми говорит: подбор матча, проверка серверов и сам матч видят один и тот же адрес. Раньше программа определялась заново для каждого адреса по таблице сокетов Windows, которая могла устареть, и часть пакетов игры могла уйти через VPN — серверы видели два адреса, и матч не начинался. Таблица теперь перечитывается, если ей больше секунды. Правила для сайтов и списки адресов по-прежнему решают для каждого адреса отдельно; QUIC (UDP 443) — как раньше.

**Игра, которая не работает напрямую, — через VPN целиком**, с 0.9.0 (Windows). Если программа, отправленная напрямую своим правилом, за 8 секунд отправила напрямую 20 UDP-пакетов и не получила ни одного ответа, или у неё не открылось напрямую соединение, пока её UDP ещё ни разу не ответил (игра запускается или ищет матч), вся программа на 30 минут идёт через VPN: её UDP-потоки переключаются сразу, новые соединения — следом. Игра, у которой матч уже идёт, не переключается — у неё сменился бы адрес. Программа появляется в списке «Не открылись напрямую», кнопка очистки возвращает её к прямому пути.

**Прямой UDP**, с 0.9.0. Сокет, которому кто-то ответил, держится 5 минут после последнего пакета (игра, тихо ждущая в лобби, сохраняет свой внешний порт), сокет без ответа закрывается через 30 секунд. Открыто не больше 1024 таких сокетов: при большем числе закрывается простаивавший дольше всех. Ошибки отправки больше не пропадают молча: они считаются, раз в минуту пишутся в журнал, а в статистике для сервера появилось поле `direct` — прямые соединения, открытые UDP-сокеты и неудачные отправки за минуту.

**IPv6 без сети IPv6**, с 0.9.0. Адаптер TurnVK показывает программам IPv6, а напрямую IPv6 идти некуда, если у компьютера его нет; через VPN идёт только IPv4. Раньше такие UDP-пакеты отбрасывались молча, и программа ждала тайм-аута, прежде чем перейти на IPv4. Теперь она сразу получает ответ «адрес недоступен» (ICMPv6) и переходит на IPv4, а вместо повторяющихся строк `listen udp6 … invalid argument` в журнале одна строка раз в 10 минут.

**Античит следует за игрой**, с 0.9.1 (Windows). Easy Anti-Cheat, BattlEye, Riot Vanguard, FACEIT и Epic Online Services работают как службы Windows: их запускает сама система, а не игра или лаунчер, поэтому правило «Игры напрямую» их не касалось. Игра шла напрямую, а её античит — через VPN, и сервер игры видел игрока по двум адресам: в Fortnite это выглядело как бесконечный «поиск игры», а у друзей в группе — «подключение к серверу». Теперь служба античита идёт тем же путём, что и игра, запущенная последней (в течение 10 минут): напрямую, через VPN по своему правилу или через VPN после того, как игра не заработала напрямую. Своё правило для самой службы по-прежнему важнее.

**Задача автозапуска**, с 0.9.1 (Windows). Раньше при каждом запуске TurnVK заново создавал задачу «Запускать вместе с Windows» с наивысшими правами. Защитник Windows после обновления 0.9.0 принял это за закрепление вредоносной программы (`Behavior:Win32/Persistence.A!ml`) и отправил файл в карантин. Теперь задача пересоздаётся, только если указывает на другой файл. Версия 0.9.0, уже попавшая в карантин, так и останется отмеченной: её можно восстановить из журнала защиты и сообщить Microsoft о ложном срабатывании. Программа не подписана сертификатом, поэтому у новой версии нет репутации у Защитника, и такое может повториться.

**«Сейчас что-то не так»**, с 0.9.2. Когда что-то лагает или не грузится, это можно отметить сразу: кнопка на главной под графиком (Windows и Android), пункт в меню значка у часов (Windows) и кнопка «Что-то не так» в уведомлении TurnVK (Android). Можно коротко написать, что не работает. Время и состояние подключения (сколько маршрутов отвечает, пинг, простой, давно ли было рукопожатие WireGuard) уходят разработчику со статистикой и попадают в журнал, а значит и в отчёт. С выключенной статистикой отметка остаётся только в журнале.

**Журнал в статистике не теряется при сбое**, с 0.9.2. При сбое за минуту появляются десятки строк, и раньше лишние (больше 40) пропадали — как раз те, что объясняли сбой. Теперь строки одного вида за минуту сливаются в одну с числом повторов, временем и текстом последней; если места всё равно не хватает, первыми уходят обычные строки (простой, учётные данные VK, проверки серверов), а отметки пользователя не уходят никогда. Минута с большим числом строк отправляется в нескольких пакетах (до трёх).

**Пропуски в статистике объяснимы**, с 0.9.2. У каждого отчёта есть номер: пропуск в номерах значит, что отчёты потерялись, пропуск во времени без пропуска в номерах — что устройство спало или не было подключено. Очередь неотправленных отчётов выросла с 30 до 60; если она всё же переполнится, следующий отчёт скажет, за какие минуты отчёты потеряны. После переподключения в журнале появляется строка, сколько не было подключения и почему закончилось прошлое.

**Сеть устройства в статистике**, с 0.9.2. Раз в минуту — тип сети (Wi-Fi, мобильная, проводная), сила сигнала, скорость и диапазон Wi-Fi (2,4 или 5 ГГц), поколение мобильной сети и сколько раз сеть сменилась. Так видно, когда лагает из-за слабого Wi-Fi или мобильного сигнала. Название сети не отправляется. На Android сигнал мобильной сети — с Android 10, скорость и диапазон Wi-Fi — с Android 12; новых разрешений приложению не нужно.

**Отчёт для разработчика**, с 0.9.2. В отчёте Android теперь есть идентификатор устройства, по которому его знает статистика сервера (в отчёте Windows он был). Во всех отчётах указан часовой пояс: время в отчёте местное, а в статистике — UTC.

**Маршруты по нагрузке**, с 0.9.3. Пока трафика мало, TurnVK держит открытыми 12 маршрутов (в режиме «Экономия» — 8), а не все. По статистике все устройства, кроме компьютера с большими загрузками, редко выходили за 4–8 Мбит/с (около 0,2 Мбит/с на маршрут) и 76–99 % минут шли медленнее 2 Мбит/с, а телефон, просыпаясь из простоя ради уведомления, 3–7 раз в час заново открывал 28 маршрутов — каждый новое выделение у VK. Теперь подключение начинается с 12 маршрутов, а после простоя к 4 оставшимся добавляется 8. Все маршруты открываются, если 3 секунды подряд идёт от 3 Мбит/с или за секунду — от 8 Мбит/с (загрузка, видео): полная скорость наступает на несколько секунд позже. Когда сглаженная скорость 10 минут остаётся ниже 1,5 Мбит/с, лишние маршруты снова закрываются. Режим «Всегда на связи» (Android), настройка «Все маршруты сразу» (Windows) и флаг `-all-routes` консольного клиента (для замеров `-download` и `-upload` он включается сам) держат открытыми все маршруты. На главном экране — «12 · по нагрузке», в статистике для сервера — секунды на лёгком уровне маршрутов в минуту (`light`).

**Маршрут заменяется после двух пропущенных проверок**, с 0.9.3. Когда туннель 2 секунды ничего не получает, хотя отправляет, клиент проверяет каждый маршрут. Раньше маршрут, не ответивший на одну проверку, сразу закрывался и заменялся новым выделением у VK: в статистике компьютер с почти пустым туннелем заменял один-два исправных маршрута каждые пару минут (до 30 в час), а дважды заменил 10–11 сразу, упёрся в ошибку 486 и четверть часа работал на 24 маршрутах. Теперь маршрут заменяется, только если не ответил на две проверки подряд. Если замолчали все маршруты одного TURN-сервера VK, а другие отвечают, новые маршруты минуту обходят этот сервер. За раз заменяется не больше четверти маршрутов, остальные ждут своего таймаута. В журнале указано, через какие TURN-серверы шли заменённые маршруты.

**Более надёжный TURN-сервер VK**, с 0.9.3. Клиент считает, как часто умирают маршруты через каждый TURN-сервер VK на час работы маршрута (старое забывается вдвое за час), и новые маршруты чаще открываются через более надёжный. По статистике через один сервер VK маршруты умирали вдвое чаще, чем через другой, а пересылать он переставал в 12 раз чаще. Менее надёжный сохраняет свою долю маршрутов (не меньше двух), чтобы сравнение продолжалось и туннель не висел на одном сервере; открытые маршруты ради этого не переносятся. Выбор меняется, только если серверы различаются хотя бы на четверть; в журнале — строка «new routes lean to TURN server …».

**Новые ключи сразу после сна**, с 0.9.3. WireGuard обновляет ключи, только когда отправляет, а ключи старше трёх минут уже не работают. Телефон, проспавший дольше, просыпался со старыми, и первые пакеты ждали рукопожатия: в статистике это задержки 9–45 секунд после пробуждения. Теперь после сна от 20 секунд, если ключам больше трёх минут, клиент заводит новое рукопожатие, как только ответил маршрут (не чаще раза в 5 минут). Строка «WireGuard: no handshake for …, the server stopped answering» у спящего телефона появлялась каждые несколько минут, хотя всё было в порядке: туннель без трафика рукопожатий не делает. Теперь она пишется, только если WireGuard отправлял данные и ничего не получил («…while sending: the server does not answer»).

**Уведомление о новой версии**, с 0.9.3. На Android приложение проверяло обновления, только когда открыт главный экран, и телефоны, которые подключаются сами, оставались на версиях с давно исправленными ошибками. Теперь, пока VPN подключён, приложение раз в 12 часов проверяет релизы на GitHub и один раз на каждую версию показывает уведомление «Доступна TurnVK …» (канал «Обновления»); нажатие открывает приложение с кнопкой «Обновить». На Windows о новой версии сообщает и значок у часов, даже если окно скрыто.

**tvkstats**, с 0.9.3. Строка старых клиентов о рукопожатии в простое больше не считается сбоем. Отрезки, где спящий телефон не прислал ни одной минуты, но записал зависание, тоже оцениваются. На лёгком уровне маршрутов в таблице — «light».

## Приложение Android

- Вкладки, как в приложении Windows: «Главная», «Серверы», «Маршруты», «Настройки», «Журнал».
- Несколько серверов: ссылки `wdtt://` сохраняются под именами, открытая извне ссылка предлагается к сохранению; ссылкой можно поделиться. Имя, которое приложение придумало само («Сервер адрес»), меняется вместе со ссылкой.
- Главный экран: кнопка подключения, время в сети, скорость загрузки и отдачи с графиком за минуту, пинг до сервера, число маршрутов, адрес в VPN, трафик, состояние каждого маршрута, протокол.
- Плитка в шторке быстрых настроек, кнопка «Отключить» в уведомлении.
- Раздельное туннелирование — те же правила, что на Windows (см. ниже): приложения, сайты, страны и списки; приложения VK идут в обход всегда. Прежний список «Приложения в обход VPN» становится правилами «напрямую».
- Подключение при включении телефона; «Постоянная VPN» и «Блокировать подключения без VPN» Android работают с TurnVK.
- Проверки в настройках: экономия заряда (может усыплять VPN) и уведомления (нужны для проверки VK).
- Журнал: копировать, отправить, очистить; кнопка «Собрать отчёт» (см. «Отчёт для разработчика»).
- По умолчанию 32 маршрута (около 45 Мбит/с); можно от 8 до 64. Пока трафика мало, открыто 12 (в режиме «Экономия» — 8), остальные открываются при загрузке (с 0.9.3).
- Обновления: приложение само проверяет релизы на GitHub; кнопка «Обновить» скачивает APK, сверяет его с `SHA256SUMS.txt` и открывает установщик Android (в первый раз Android попросит разрешить TurnVK устанавливать приложения). Пока VPN подключён, приложение проверяет релизы раз в 12 часов и само сообщает о новой версии уведомлением (с 0.9.3).
- С 0.4.0 релизы подписаны постоянным ключом и ставятся поверх. На 0.4.0 с более ранней версии нужно один раз удалить старую.
- Ссылка `wdtt://`, открытая извне, обрабатывается один раз: при повторном открытии приложения из недавних оно больше не спрашивает про сервер.
- Сервер, добавленный с главного экрана, сразу выбирается: кнопка подключения становится доступна без захода во вкладку «Серверы» (до 0.5.0 главный экран не обновлялся после сохранения).

## Приложение Windows

`TurnVK.exe` — окно с теми же вкладками и настройками, что на Android, и VPN для всего компьютера через Wintun (`wintun.dll` встроен и кладётся рядом с программой при запуске).

- При запуске просит права администратора (окно UAC): без них Windows не даёт создать сетевой адаптер. Адаптер «TurnVK» существует только на время подключения.
- Весь IPv4 идёт в туннель двумя маршрутами `/1`, DNS — через сервер. IPv6 туннель не везёт: адаптер забирает и его, чтобы он не шёл мимо VPN (с раздельным туннелированием IPv6 идёт напрямую там, где правила отправляют соединение напрямую, см. ниже).
- Собственные соединения TurnVK (VK, TURN, DNS для имён VK) привязаны к сети, через которую Windows ходит в интернет (`IP_UNICAST_IF`); при смене сети TurnVK переподключается.
- Если работает другой VPN (v2RayTun, OpenVPN, WireGuard…), приложение предупреждает: его более узкие маршруты забирают большую часть трафика, а DNS уходит в TurnVK, и программы (например, Discord) ломаются. Подключение при запуске в этом случае не выполняется.
- `TurnVK.exe wdtt://…` — добавить (или выбрать) сервер и подключиться.
- Крестик окна (с 0.8.0) прячет окно, а TurnVK остаётся подключённым: значок — в области уведомлений рядом с часами (подсказка показывает состояние). Щелчок по значку открывает окно, правая кнопка — меню «Открыть TurnVK», «Подключить»/«Отключить», «Выйти». Если VK просит проверку, окно открывается само. Повторный запуск `TurnVK.exe` показывает окно уже работающей копии. Выходить при закрытии окна — выключатель «Работать в фоне после закрытия окна» в настройках.
- «Запускать вместе с Windows» (Настройки): задача в Планировщике заданий («TurnVK») запускает `TurnVK.exe --autostart` через 10 секунд после входа в Windows, с наивысшими правами — поэтому без окна UAC. Окно открывается свёрнутым, приложение ждёт сети (до двух минут) и подключается к выбранному серверу. Задача работает и от батареи, без ограничения времени. Если программу перенесли, задача при следующем запуске указывает на новое место.
- Настройки — `%APPDATA%\TurnVK\settings.json`, журнал — `%LOCALAPPDATA%\TurnVK\turnvk.log`. Номер устройства и гостевые токены VK общие с консольным клиентом.
- Нужен Microsoft Edge WebView2 Runtime (в Windows 10/11 обычно уже есть).
- Порядок настройки адаптера: сначала маршруты, потом адрес. Установка маршрутов стирает все маршруты адаптера, в том числе локальный маршрут адреса (`10.66.67.x/32`), который Windows создаёт вместе с адресом; без него Windows отбрасывает все ответы как «Not locally destined» — подключено, но ничего не открывается (так было до 0.4.1).
- `TurnVK.exe --debug-run` — проверка для разработчика: подключается, пишет в журнал первые пакеты в обе стороны, состояние адреса и маршрутов адаптера и пакеты, которые отбросила Windows (pktmon), затем отключается и закрывается.
- Через 15 секунд после подключения приложение проверяет интернет через туннель (DNS туннеля, доступ к сайтам, внешний адрес) и пишет результат в журнал; если интернет не работает, на главной появляется предупреждение.
- Обновления: при запуске и раз в 6 часов приложение проверяет релизы на GitHub; кнопка «Обновить» скачивает новую версию, сверяет её с `SHA256SUMS.txt`, заменяет программу и перезапускает её (без нового окна UAC). Проверить вручную — «Настройки» → «Проверить обновления». О новой версии сообщает и значок у часов (с 0.9.3).
- Маршруты по нагрузке (с 0.9.3): пока трафика мало, открыто 12 маршрутов, остальные открываются за несколько секунд, когда начинается загрузка. Выключатель «Все маршруты сразу» в настройках держит открытыми все.

## Раздельное туннелирование

С 0.6.0, в приложениях Windows и Android; режимы, проверка «Куда пойдёт сайт?» и повтор через VPN — с 0.7.0; режим «Только выбранные программы», режим по сети, подсказки к правилам, правило для сайта из списка соединений, закрытые соединения, повтор QUIC, IPv6 напрямую и плитка Android — с 0.8.0.

Вкладка «Маршруты»: выбранные программы и сайты идут напрямую или через VPN, остальные — как задано («Остальные программы»: через VPN или напрямую). Локальная сеть по умолчанию идёт напрямую.

- **Режимы** (с 0.7.0) — обычные настройки одним выбором: «Всё через VPN» (раздельное туннелирование выключено), «Только заблокированное через VPN» (остальное напрямую, списки `geosite:ru-blocked` и `geoip:ru-blocked` — через VPN), «Российское напрямую» (остальное через VPN, `geoip:ru`, `geosite:category-ru` и сайты `.ru`, `.su`, `.рф` — напрямую), «Свои правила». Режим только задаёт «остальные» и добавляет (или включает) свои списки; правила для программ, сайтов и другие списки остаются. Какой режим выбран, видно по правилам: выключите его список — и это уже «Свои правила».
- **Только выбранные программы через VPN** (режим, с 0.8.0): через VPN идут только программы (приложения) с правилом «Через VPN», всё остальное — напрямую, что бы ни говорили правила для сайтов и списки: они действуют только внутри выбранных программ. На Android остальные приложения не входят в туннель вовсе (`addAllowedApplication`), даже если есть сайты «через VPN», — это самый экономный режим.
- **Режим по сети** (с 0.8.0): режим для Wi-Fi, мобильной сети или кабеля, на Windows — и для отдельной сети Wi-Fi по имени («этот Wi-Fi»). В сети с правилом её режим применяется поверх ваших правил так же, как при выборе режима (ваши правила для программ и сайтов остаются); правило для имени Wi-Fi сильнее правила для Wi-Fi вообще; в сети без правила действуют ваши правила как есть. TurnVK узнаёт сеть при подключении и при каждой её смене: Windows — по типу адаптера, через который идёт интернет, и имени сети из `netsh wlan show interfaces`; Android — по типу сети (имя Wi-Fi Android даёт только с доступом к местоположению, его TurnVK не просит). Если на Android от смены сети меняется, какие приложения пускаются в туннель, TurnVK переподключается сам. Списки, нужные режимам сетей, скачиваются заранее.
- **Подсказки к правилам** (с 0.8.0): под правилом написано, если оно ничего не меняет («остальные программы и так идут через VPN»), лишнее (уже покрыто правилом для папки или для основного сайта), исключение из другого правила, если его перебивают правила для сайтов («кроме сайтов, которые правила для сайтов и списки отправляют напрямую: они сильнее правил для программ») или если при совпадении двух списков победит VPN.
- **На главной** — строка «Раздельное туннелирование» с режимом и числом правил и переключатель: выключить всё одним касанием и включить обратно. На Android, если от этого меняется, какие приложения Android пускает в туннель, там же появляется «Переподключить».
- **«Куда пойдёт сайт?»** — проверка без подключения к сайту: введите сайт, ссылку или адрес (и, если нужно, выберите программу из правил) — TurnVK покажет путь и причину по текущим правилам («список geosite:ru-blocked», «правило для game.exe», «нет правила для сайта: всё остальное идёт через VPN»). Адреса сайта для стран и списков адресов узнаются через DNS (на Android — через VPN, пока он подключён); если списки ещё не скачаны или адрес неизвестен, это сказано отдельно.
- **QUIC** (с 0.8.0): соединение QUIC (HTTP/3, UDP 443), отправленное напрямую к настоящему адресу, тоже проверяется: если за 2 секунды с сайта не пришло ни одного пакета, следующие пакеты идут через VPN, начиная с копий первых (программа всё равно повторяет их сама), и сайт запоминается на 30 минут для QUIC. Отказ QUIC не отправляет через VPN соединения TCP с тем же сайтом: в сетях, где UDP не проходит вовсе, иначе через VPN ушло бы всё. Сайт за адресом-заменителем так не переключается (VPN не знает заменителя): браузер сам переходит на TCP, а TCP проверяется как ниже.
- **Не открылся напрямую — через VPN** (с 0.7.0, включено по умолчанию). Сайт, который идёт напрямую (порты 443, 80, 8443, 8080), открывается так: соединение принимается внутри TurnVK, читаются его первые байты, затем TurnVK соединяется с сайтом напрямую (не дольше 5 секунд) и, для HTTPS, ждёт ответа на TLS ClientHello (тоже до 5 секунд). Если сайт не ответил, отказал, сбросил или закрыл соединение после приветствия — так обычно выглядит блокировка, — то же соединение открывается через VPN с теми же первыми байтами, и программа ничего не замечает, кроме задержки. Для обычного HTTP проверяется только само соединение: запрос нельзя отправлять дважды. Сайт запоминается на 30 минут: его следующие соединения сразу идут через VPN. На вкладке «Маршруты» появляется «Не открылись напрямую» со списком таких сайтов и кнопкой «… — через VPN» (правило для основного домена: `googlevideo.com` для `rr3---sn-….googlevideo.com`). Локальная сеть так не проверяется. Выключается переключателем в настройках вкладки.

- **Как решается путь.** Адаптер TurnVK по-прежнему забирает весь трафик. Между адаптером и WireGuard стоит маршрутизатор соединений (`core/split`): на первом пакете каждого нового соединения он находит программу по её локальному порту (таблицы сокетов Windows, как `netstat -ano`) и решает, куда его отправить. Соединения через VPN уходят в WireGuard без изменений. Прямые принимаются внутри TurnVK и открываются заново из сокетов, привязанных к физической сети (`IP_UNICAST_IF`): TCP — через встроенный стек gVisor (сначала соединение с адресатом, потом ответ программе; если адресат отказал — программа получает сброс, как без VPN), UDP — без стека, один внешний сокет на сокет программы, так что игра со многими серверами и игроками держит один внешний порт. Решение принимается до того, как первый пакет покинул компьютер, для любого адреса, TCP и UDP: заранее ничего не настраивается и ничего не проскакивает.
- **Правила.** Программа (`.exe`) или папка (все программы в ней и во вложенных папках — удобно для игр, где лаунчер, античит и клиент — разные файлы). Галочка «и программы, которые она запускает» распространяет правило на дочерние процессы (по дереву процессов с проверкой времени запуска). Правило программы сильнее правила папки, вложенная папка сильнее внешней, своё правило сильнее родительского. Адреса самого туннеля и его DNS всегда идут через VPN; проверки самого TurnVK — тоже.
- **Сайты.** Правило для имени действует на все поддомены (`example.com` — это и `www.example.com`, `su` — все сайты `.su`), в любой программе, и сильнее правил для программ. Из ссылки берётся только имя сайта: путь страницы внутри HTTPS не виден. Кнопки `.ru`, `.su`, `.рф` — быстрые правила «напрямую».
  - Сайт напрямую: Windows спрашивает DNS туннеля, и TurnVK отвечает на такие вопросы сам — адресом-заменителем из `198.18.0.0/15`, своим для каждого имени (TTL 1 с). Соединение с этим адресом — ровно этот сайт, даже если его настоящие адреса делит с другими CDN. TurnVK соединяется с сайтом по имени, разрешая его мимо туннеля (DNS Яндекса, как имена VK), так что CDN отдаёт ближайшие к компьютеру серверы. AAAA и HTTPS-записи для таких имён отвечаются пусто, чтобы IPv6 и подсказки адресов не шли в обход.
  - Сайт через VPN (когда остальные идут напрямую): имя разрешается через VPN как обычно, а маршрутизатор запоминает адреса из ответа и направляет соединения с ними в VPN. Здесь общий адрес CDN может увести в VPN и соседний сайт — ошибка в безопасную сторону.
  - Браузеры сами переходят на зашифрованный DNS (DoH), если DNS системы его поддерживает (1.1.1.1 поддерживает), и тогда правила по именам ничего не видят. Пока есть сайты «напрямую», HTTPS и DNS-over-TLS к DNS-серверам туннеля отклоняются — браузер сразу возвращается к обычному DNS; Firefox получает «нет такого имени» на `use-application-dns.net`. Свой DoH, настроенный в браузере вручную, это не отключает.
  - При подключении, отключении и смене правил для сайтов TurnVK очищает кэш DNS Windows (браузер держит свой кэш ещё до минуты).
- **Страны и списки сайтов.** Готовые списки v2ray (`geoip.dat`, `geosite.dat` из [runetfreedom/russia-v2ray-rules-dat](https://github.com/runetfreedom/russia-v2ray-rules-dat), пересобираются каждые 6 часов): адреса любой страны (`geoip:de`), сервисов (`geoip:telegram`), категории сайтов v2fly (`geosite:youtube`, `geosite:discord`) и российские списки — заблокированное в России (`geosite:ru-blocked`, `geoip:ru-blocked`) и работающее только из России (`geosite:ru-available-only-inside`). Кнопки: «Россия напрямую», «Заблокированное в России — через VPN», «Работает только из России — напрямую», сервисы; любая страна или список — по имени с подсказками.
  - Списки сайтов работают как правила для сайтов (адреса-заменители, сильнее правил для программ); свои правила для сайтов сильнее списков. Страны и адреса сервисов — после правил для программ: они уточняют «остальные программы» и не трогают программу, которой задан свой путь. Если сайт или адрес есть в нескольких списках, побеждает VPN.
  - Списки скачиваются только через VPN (собственные соединения TurnVK всегда идут в туннель): через 5 секунд после подключения и затем раз в 12 часов, а также кнопкой «Обновить» и при выборе списка из ещё не скачанного файла. Сначала скачивается контрольная сумма (несколько байт); файл качается, только если он изменился, и заменяет старый, только если целиком совпал с суммой. Файлы лежат в `%LOCALAPPDATA%\TurnVK\lists`; из них загружаются только выбранные списки. Адреса IPv6 из списков пропускаются, как и весь IPv6.
- **Android.** Вкладка «Маршруты» с теми же правилами; вместо программ и папок — приложения. Маршрутизатор соединений тот же (`core/split` перед WireGuard), приложение соединения он находит по его UID: `ConnectivityManager.getConnectionOwnerUid` (Android 10+), раньше — таблицы `/proc/net`. Приложения с общим UID считаются одним приложением.
  - Что Android может сделать сам, делает он: приложение «напрямую» не пускается в туннель вовсе (`addDisallowedApplication`) — его трафик не тратит ни заряд, ни процессор на TurnVK. А при «Остальные — напрямую» в туннель пускаются только приложения «через VPN» (`addAllowedApplication`). Это возможно, пока ни одно правило не может вернуть трафик такого приложения в VPN: сайт или список сайтов «через VPN» (они сильнее правил для приложений) — тогда приложение входит в туннель и путь каждого соединения решает маршрутизатор; страна «через VPN» так же влияет на «остальные». Какие приложения Android пускает в туннель, задаётся при подключении: если правка это меняет, вкладка предлагает переподключиться. Остальные правки действуют сразу.
  - Кэш DNS Android хранит ответы по их TTL; адреса-заменители живут 1 секунду, так что смена правил для сайтов вступает в силу почти сразу. «Частный DNS» в режиме «Автоматически» пробует DoT на DNS туннеля — он отклоняется так же, как DoH, и Android возвращается к обычному DNS.
  - Собственные соединения TurnVK на Android идут мимо VPN (чтобы проверка VK открывалась и без туннеля), поэтому списки скачиваются через соединения, которые маршрутизатор сам открывает в туннель (как при чтении имени сайта, см. ниже); если через VPN не вышло — напрямую. Пока VPN подключён: через 5 секунд после подключения, потом файл, скачанный меньше 3 дней назад, не трогается (файл сайтов — около 90 МБ); кнопка «Обновить» скачивает заново. Файлы — в личной папке приложения.
- **Имя сайта из соединения.** Если программа узнала адрес сайта не через DNS туннеля (свой зашифрованный DNS, «Частный DNS» Android в строгом режиме, адреса, встроенные в программу), имени у адреса нет. Тогда, если правило для сайтов может поменять путь, TurnVK читает имя из начала соединения: имя сервера в TLS ClientHello (HTTPS — порты 443 и 8443), заголовок Host (HTTP — 80 и 8080), то же ClientHello в первом пакете QUIC (UDP 443; его шифр выводится из открытого идентификатора соединения, RFC 9001, версии 1 и 2).
  - TCP: соединение принимается внутри TurnVK, как прямое, его первые байты читаются (не дольше секунды: протоколы, где первым говорит сервер, просто ждут секунду) — и оно открывается напрямую или через VPN, первые байты уходят первыми. Через VPN маршрутизатор открывает соединение сам, из своего стека TCP, с адреса и порта программы, и отдаёт пакеты WireGuard так, будто их отправил компьютер; ответы забирает из потока WireGuard. Для этого, начиная с первого такого соединения, адаптер читает отдельная горутина, и маршрутизатор подмешивает в поток к WireGuard свои пакеты.
  - QUIC: первые пакеты держатся до 300 мс, пока не соберётся ClientHello (браузеры делят большое ClientHello на два пакета и перемешивают его части), потом все уходят одним путём, по порядку.
  - Если имени нет (зашифрованное ClientHello — ECH, адрес вместо имени, другой протокол), соединение идёт тем путём, которым пошло бы без имени. Узнанные так имена видны в «Соединениях сейчас» с пометкой «имя из соединения».
- **Соединения.** Пока вкладка открыта, видно, какие программы куда соединяются, каким путём и почему; кнопки «Напрямую» / «Через VPN» создают правило для программы. С 0.8.0 у каждого соединения с известным сайтом есть кнопка правила для этого сайта (основной домен, в другую сторону: «googlevideo.com → VPN») — например, чтобы лаунчер шёл через VPN, а его CDN напрямую. Фильтры: все, напрямую, через VPN, «не открылись напрямую». «Закрытые за час» — соединения, которые уже закончились (за последний час, пока VPN подключён), сгруппированные по программе, сайту и пути, с числом соединений: видно, куда ходила игра, после того как её закрыли.
- Правила действуют на новые соединения сразу, без переподключения; открытые соединения сохраняют свой путь.
- **IPv6** (с 0.8.0). Туннель по-прежнему везёт только IPv4, но адаптер забирает и IPv6. Соединение IPv6 TCP или UDP, которое правила отправляют напрямую, открывается напрямую, как IPv4 (имя сайта для правил — из ответов AAAA). Соединение IPv6, которое должно идти через VPN, получает сброс сразу (TCP; UDP отбрасывается), и программа без ожидания переходит на IPv4. Адрес адаптера для IPv6 — локальный (ULA), поэтому программы выбирают IPv4, когда он есть: IPv6 нужен прежде всего сайтам и серверам, у которых IPv4 нет. Пакеты IPv6 с дополнительными заголовками и фрагменты идут, как раньше, в туннель и отбрасываются.
- **Размер списков** (с 0.8.0): рядом со списком — сколько в нём сайтов или диапазонов адресов; большой (больше 200 000 записей, например `geosite:ru-blocked-all`) помечен: он занимает больше памяти и дольше загружается. До первого скачивания сказано, сколько весит файл (сайты — около 90 МБ). На Android списки по умолчанию скачиваются только по Wi-Fi: в мобильной сети они ждут Wi-Fi, кнопка «Обновить» скачивает сразу (выключатель «Скачивать списки только по Wi-Fi»).
- **Плитка Android** «TurnVK: маршруты» (с 0.8.0) в быстрых настройках включает и выключает раздельное туннелирование; если от этого меняется, какие приложения пускаются в туннель, TurnVK переподключается. Пока правил нет, плитка открывает приложение.
- Ограничения: IPv6 — только напрямую (см. выше); фрагменты больших UDP-датаграмм собираются для прямых соединений; ICMP (ping) идёт через VPN. Если сокет закрылся раньше, чем Windows его показала, программа не определяется, и соединение идёт по правилу «Остальные программы». DNS через TCP правила по именам не видят (Windows пользуется им редко), но такие соединения узнаются по имени из соединения.

## Отчёт для разработчика

На вкладке «Журнал» обоих приложений кнопка «Собрать отчёт» собирает за несколько секунд текст для разработчика и копирует его (на Windows он ещё сохраняется в `%LOCALAPPDATA%\TurnVK\report-….txt`, на Android им можно поделиться). В отчёте:

- система: версия Windows или Android, устройство; на Windows — адаптеры, их адреса и DNS, маршруты, которые забирают интернет, другой VPN и сеть, к которой привязаны маршруты TurnVK; на Android — сети и их тип;
- настройки и сервер (адрес, порты, число звонков VK, есть ли ключ сервера — без пароля и звонков);
- подключение: маршруты по серверам TURN с пингом и потерями, ответил ли сервер на рукопожатие WireGuard и когда, трафик через туннель каждые 10 секунд за последние 15 минут;
- проверки: DNS и API VK; на Windows при подключении — ещё DNS туннеля, доступ в интернет, внешний адрес (совпадает ли с сервером), Discord и YouTube через VPN. На Android приложение само не ходит через свой VPN, поэтому проверки через туннель там не делаются;
- последние 400 строк журнала.

Если отчёт собран после отключения, на Windows в него попадает последнее подключение (маршруты, рукопожатие, трафик).

Ссылки `wdtt://`, звонки VK, токены и длинные ключи заменяются на `<hidden>`. В журнал движок теперь пишет первое рукопожатие WireGuard (или что сервер не ответил за 15 секунд) и раз в минуту — трафик, число маршрутов и возраст рукопожатия.

## Статистика для сервера

С 0.5.0 клиент раз в минуту отправляет серверу TurnVK короткий отчёт о подключении — сообщением `STATS` прямого протокола, по своим же маршрутам через TURN VK. Сервер подтверждает его (`STATSACK`); до 60 неподтверждённых отчётов ждут в очереди и уходят повторно, а что случилось с неудачным подключением, уходит со следующим удачным. Отчёт — JSON, сжатый zlib, не больше 1000 байт: трафик туннеля за минуту, маршруты (открыто, живых, нужно), задержка средняя и худшая, потери, скорость и потери отдачи, переподключения маршрутов, возраст рукопожатия WireGuard, сон устройства, капча, число TURN-серверов VK, версия приложения и ОС, сеть устройства (тип, сигнал, смены сети), секунды простоя и лёгкого уровня маршрутов, номер отчёта, а также строки журнала (строки одного вида за минуту сливаются в одну, при нехватке места первыми уходят обычные; ссылки, ключи и токены вырезаются) и отметки «Сейчас что-то не так». Адресов сайтов и содержимого трафика в нём нет.

Выключается в настройках («Отправлять статистику серверу») или флагом `-no-server-stats` консольного клиента. Стандартному серверу отчёты не отправляются; сервер TurnVK старее 1.5.0 их не подтверждает, и после шести неподтверждённых клиент пробует снова раз в 10 минут (до 0.8.0 — переставал до следующего подключения, и сервер, обновлённый во время подключения, отчётов не получал). Сервер TurnVK из `wdtt-router` до 1.5.1 после обновления панели продолжал работать старой версией до следующего применения настроек или перезагрузки — поэтому статистика могла не появиться вовсе. Хранение, лимит размера и очистка — в панели сервера (`wdtt-router`, Настройки → «Статистика TurnVK»).

Разобрать архив статистики из панели помогает `tvkstats`: без параметров он показывает устройства (версия, пинг, потери, сбои, отметки), с `-dev` — одно устройство по 10 минут, его события и отметки, и для каждого плохого отрезка, на чьей он стороне: сеть или провайдер устройства (сбой только у него, слабый сигнал), сервер или VK (у всех сразу) или сам TurnVK (туннель замолчал, хотя маршруты отвечали). `-at 08:30` показывает поминутно ±15 минут вокруг времени. Строки старых клиентов «WireGuard: no handshake for …, the server stopped answering» (так телефон без трафика писал каждые несколько минут) сбоем не считаются.

```
go run ./cmd/tvkstats -tz +3 turnvk-stats.zip
go run ./cmd/tvkstats -tz +3 -dev d4f5 -at 08:30 turnvk-stats.zip
```

## Консольный клиент (Windows, Linux, macOS)

```bash
turnvk -link "wdtt://…"                 # SOCKS5-прокси на 127.0.0.1:1080
turnvk -link "wdtt://…" -test           # проверить туннель (IP выхода, DNS) и выйти
turnvk -link "wdtt://…" -download URL   # замер скорости
turnvk -link "wdtt://…" -download URL -stats -ping 10.66.67.1   # скорость, потери и пинг по секундам
turnvk -link "wdtt://…" -upload 20 -stats                       # отдача 20 МБ
```

Встроенный стек TCP консольного клиента (gVisor) настроен под VK TURN: CUBIC и буферы по 4 МБ (до 16 МБ) вместо Reno и 1 МБ. Отдача с 16 маршрутами на тестовом сервере: 2–8 Мбит/с с настройками gVisor, 11–12 с CUBIC и буфером 1 МБ, 13–17 с буферами 4 МБ. Главное — буферы: отправитель держит в пути не больше буфера, а при пачках потерь VK большая часть ждёт повтора. Для сравнений: `TURNVK_TCP=off` (настройки gVisor) или, например, `TURNVK_TCP=cc=reno,buf=1M`; `TURNVK_SCORE=off` — без оценки TURN-серверов.

Замер по сценариям (простой туннель, загрузка с 16 и 32 маршрутами, короткая загрузка 5 МБ, отдача, 2 % потерь на сервере, перезапуск сервера) — `scripts/bench.sh`. Скорость он меряет до `scripts/bench-endpoint` — маленького сервера, который запускается на тестовом сервере на адресе туннеля: публичные замеры (Cloudflare) после десятков прогонов начинают отказывать и добавляют шум интернета. На сервере с fail2ban частые подключения по SSH (сценарии с потерями и перезапуском) могут привести к временному бану адреса. С `BENCH_LOCAL=1` скрипт запускается на самом тестовом сервере (клиент оттуда тоже идёт через TURN VK): замеры не зависят от домашней сети, а сценарии с потерями и перезапуском не открывают SSH. Он пишет строку на сценарий в `bench-results.txt`, а полные журналы клиента — в `bench-results-logs/`. Учётные данные VK сохраняются, поэтому повторные прогоны в пределах часа не обращаются к VK.

Флаги: `-sessions` (по умолчанию 16), `-stats` (раз в секунду: скорость, маршруты, их задержка и потери; в конце — строка `ROUTE` на каждый маршрут: TURN-сервер, задержка, потери), `-ping адрес` и `-pings N` (пинг через туннель во время проверки), `-obfs audio|video`, `-device-id`, `-turn host:port`, `-dns`, `-no-server-stats`, `-all-routes` (держать открытыми все маршруты; для `-download` и `-upload` включается сам). Если VK просит капчу, на Windows открывается окно с ней (WebView2). Гостевые токены VK хранятся в `%LOCALAPPDATA%\turnvk\vk-guests.json` (Linux: `~/.cache/turnvk/`), так что повторный запуск капчу не вызывает.

## Дальше

- Windows: значок в области уведомлений, блокировка трафика мимо VPN.
- Android: сканирование QR-кода со ссылкой.
- Протокол: число маршрутов по нагрузке; FEC для сетей с большими потерями; медленное хеширование пароля для внешнего слоя. Запасные маршруты (открытые заранее) отложены: каждый требует учётных данных VK сверх нынешних, то есть нового гостя и, возможно, капчи; вместо них — быстрая замена (см. «Скорость и задержка»).
- Справедливая очередь по соединениям на сервере (звонок не дёргается во время большой загрузки): отдать очередь ядру (`fq_codel` на `wdtt1`) нельзя — библиотека WireGuard при заполнении своих очередей отбрасывает пакеты, а не придерживает чтение. Нужен свой планировщик перед шифрованием; отложено, пока не будет способа измерить пользу.
- Редкие выбросы пинга до 110–200 мс в замерах — это домашняя сеть: в те же моменты так же вырастает задержка до TURN-сервера VK напрямую, без туннеля.

## Капча VK: как её стало меньше

VK спрашивает капчу только на первых трёх шагах входа в звонок (анонимный токен, превью звонка, токен звонка). Эти токены живут сутки, а учётные данные TURN, которые из них получаются, — 8 часов (срок зашит в имени пользователя TURN). Поэтому:

- токены звонка сохраняются (`vk-guests.json`) и используются повторно: новые учётные данные TURN берутся одними шагами calls.okcdn.ru, где капчи нет, в том числе после перезапуска приложения;
- если VK перестал принимать сохранённый токен, клиент один раз входит заново (и только тогда может понадобиться капча);
- пока прежние учётные данные TURN действуют, новые запрашиваются в фоне: неотвеченная капча не мешает переподключениям, а пропущенная не спрашивается снова 15 минут;
- на Android, когда капча всё же нужна, приходит уведомление «Нужна проверка VK»; оно исчезает, как только проверка пройдена, отменена или больше не нужна.
