# TurnVK

Клиент для серверов WDTT: WireGuard через TURN-серверы звонков VK. С сервером TurnVK в [wdtt-router](https://github.com/Jetvac/wdtt-router) работает по собственному прямому протоколу, со стандартным сервером WDTT — по обычному (DTLS + GETCONF). Принимает те же ссылки `wdtt://`.

Платформы: Android (приложение) и Windows (приложение с окном и VPN для всего компьютера; есть и консольный клиент с SOCKS5-прокси). Ядро одно на все платформы, оформление приложений одинаковое.

## Как это работает

```
приложение ─► WireGuard (в процессе) ─► маршруты ─► TURN VK ─► сервер WDTT ─► интернет
                                          │
                                          └─ каждый маршрут: UDP-сокет → выделение на TURN VK →
                                             RTP-маскировка (ChaCha20-Poly1305) → HELLO (прямой протокол)
                                                                               или DTLS 1.2 → GETCONF (стандартный)
```

1. По ссылке звонка VK клиент заходит в звонок анонимным гостем (как веб-клиент VK Звонков) и получает учётные данные TURN.
2. Открывает несколько маршрутов, каждый — через своё выделение (allocation) на TURN-сервере VK. Весь трафик идёт только через TURN VK, напрямую к серверу клиент не подключается.
3. WireGuard работает внутри процесса и передаёт пакеты прямо в маршруты, без локального UDP-порта.

## Прямой протокол (сервер TurnVK)

Стандартный протокол открывает на каждом выделении отдельное DTLS-соединение и повторяет на нём GETCONF; пропало выделение — пропало соединение, перезапустился сервер — рвутся все. Прямой протокол убирает DTLS:

- **Соединение — это сама сессия WireGuard**, сквозная между клиентом и сервером. Маршруты через TURN VK к ней только подключаются: одно сообщение HELLO, один ответ WELCOME. Маршрут можно потерять или добавить без рукопожатия.
- **Шифрование в два слоя.** Внутри — WireGuard (Curve25519, ChaCha20-Poly1305, прямая секретность). Снаружи — RTP-маскировка под аудио или видео звонка, тоже ChaCha20-Poly1305 по ключу из пароля. Без пароля сервер не отвечает вообще, порт выглядит закрытым.
- **Ключ WireGuard клиент создаёт сам** при каждом подключении и отправляет серверу только открытую часть. Сервер больше не выдаёт закрытых ключей, и даже знающий пароль не прочитает чужой трафик.
- **Ключ сервера в ссылке** (`?pk=…`, панель добавляет его в ссылки TurnVK). Клиент сверяет его и не подключится к подменённому серверу, даже если у подменившего есть пароль. Без `?pk=` клиент сам определяет, понимает ли сервер прямой протокол, и иначе переходит на стандартный.
- **Живость каждого маршрута.** Каждые 4 с — PING с замером задержки. Клиент и сервер шлют трафик только по отвечающим маршрутам. Когда туннель замолкает, клиент проверяет маршруты и заменяет только умершие, остальные продолжают работать. Закрывая маршрут, клиент сообщает об этом серверу (BYE).
- **Обратный трафик по всем маршрутам.** Сервер распределяет ответы устройству по всем его живым маршрутам, а не только по последнему.
- **Перезапуск сервера** стоит одного HELLO на маршрут: сервер отвечает RESET на пакет неизвестного маршрута, клиент тут же подключает его снова и обновляет ключи WireGuard.
- **Защита от повтора HELLO** (метка времени и одноразовое число). Если часы устройства сбиты, сервер сообщает своё время, и клиент поправляется сам.
- Новое подключение того же устройства (перезапуск приложения) сразу забирает адрес; маршруты прежнего запуска сервер закрывает.

## Чем отличается от исходного клиента

| | Исходный клиент | TurnVK |
| --- | --- | --- |
| Путь пакета | WireGuard-приложение → UDP 127.0.0.1:9000 → отдельный процесс клиента → сессии | WireGuard и сессии в одном процессе, без локального сокета и лишних копий |
| Распределение по сессиям | по 12 пакетов на сессию по кругу | каждый пакет — в тот маршрут, где он дойдёт раньше (учитывается, сколько уже отправлено в маршрут, и время прохождения); короткие пакеты не ждут за загрузкой. Сервер TurnVK к тому же ведёт каждый маршрут с той скоростью, которую VK пропускает без потерь (см. «Скорость и задержка») |
| Перезапуск сервера | клиент ждёт до 30 минут (таймаут чтения) или 90 с до перезапуска сторожем; потом ещё ~16 с на рукопожатие WireGuard | закрытие сессий сервером замечается сразу, сброс устаревшей сессии — по первому пакету; рукопожатие WireGuard — сразу, без ожидания таймаута |
| Сервер замолчал без сброса | — | переподключение через 8 с, если пакеты уходят, а ответа нет; с сервером TurnVK — проверка маршрутов через 2 с и замена только умерших |
| Пропало одно выделение TURN | соединение на нём рвётся | с сервером TurnVK трафик уходит на остальные маршруты, умерший заменяется |
| Ключи | сервер присылает закрытый ключ WireGuard | с сервером TurnVK ключ создаётся на устройстве, ключ сервера сверяется со ссылкой |
| Смена сети (Wi-Fi ↔ LTE) | ждёт, пока сессии отвалятся | сессии переоткрываются сразу |
| Учётные данные VK | группа из 9 сессий на набор, новый гость на каждый запрос | группа из 8 сессий на набор, до 16 сессий на гостя звонка (больше VK не даёт: ошибка 486); учётные данные обновляются раз в час, а не каждые 8 минут, и сохраняются между запусками — перезапуск в пределах часа обходится без запросов к VK |
| Капча VK | автоматический обход (подделка отпечатка браузера, решение головоломки, автонажатие) | капча показывается пользователю, на Android — с уведомлением; после проверки подключение продолжается само. Гостевые токены VK живут сутки и сохраняются на устройстве, поэтому капча бывает не чаще раза в сутки на звонок, а не при каждом обновлении учётных данных и перезапуске |
| MTU | не ниже 1280, даже если сервер прислал меньше | берётся из конфигурации сервера |

## Замеры

Windows, домашний интернет, реальные TURN-серверы VK, тестовый сервер wdtt-router (1 vCPU), выход через второй сервер:

- подключение — 1,2–1,5 с, первый запрос — около 0,2 с;
- скачивание 50 МБ: 16 сессий — 23,6 Мбит/с, 24 сессии — 31,0 Мбит/с;
- плановый перезапуск сервера — теряется один запрос, который был в пути; аварийное завершение сервера (SIGKILL) — туннель восстанавливается примерно через 2 с после запуска сервера.

Прямой протокол, 14.11.2026: тестовый сервер TurnVK в Германии, 4 маршрута, запрос раз в секунду:

- подключение — 1,3–1,8 с;
- перезапуск сервера посреди работы — 40–42 запроса из 41–42 прошли;
- один маршрут перестал пропускать пакеты (заблокирован на сервере) — 85 из 86 запросов прошли, маршрут заменён сам; на стандартном протоколе тот же сбой давал каскад переподключений;
- скачивание через 8 маршрутов — 11–13 Мбит/с (стандартный протокол в те же минуты — 9–11 Мбит/с; предел задают TURN-серверы VK).

## Скорость и задержка

VK ограничивает каждое выделение TURN примерно 1,5–2 Мбит/с, и ограничивает жёстко: всё, что пришло сверх нормы пачкой, отбрасывается почти целиком, пока запас не восстановится. Загрузка без управления идёт рывками — секунда на 60 Мбит/с, секунда с потерей 90 % пакетов. TCP после таких потерь замирает, пинги теряются или ждут. Поэтому:

- сервер TurnVK отправляет в каждый маршрут ровно с той скоростью, которую VK пропускает: очередь копится на сервере, а не теряется у VK;
- в этой очереди короткие пакеты (пинг, подтверждения TCP, DNS, игры, звонки) идут первыми, а крупные, ждущие дольше 60 мс, сбрасываются — TCP замедляется раньше, чем вырастет задержка;
- получатель, пока идут данные, до 20 раз в секунду сообщает по каждому маршруту (FEEDBACK): номер последнего пакета, сколько он ждал отправки отчёта, сколько пакетов дошло и сколько потеряно. Отправитель помнит, когда отправил этот пакет, и получает задержку самих данных. Раз в 100 мс скорость маршрута меняется: при потерях больше 5 % (на сотню пакетов) — на 15 % ниже, при росте задержки на 25 мс над обычной — на 8 % ниже (но из-за одной задержки не ниже половины начальной скорости), пока маршрут чист, быстр и занят — на 2 % выше. Случайные потери мобильной сети в пару процентов скорость не снижают — снижают только выбросы ограничителя VK;
- так же работает и отдача: клиент ведёт маршруты по отчётам сервера. Крупные пакеты отдачи идут по одному маршруту, пока его запас не кончится: TCP-отправитель здесь — само устройство, и многие стеки (в консольном клиенте, старые Windows и Android) принимают переупорядочивание за потери и замедляются (замер: вдвое быстрее, чем при сериях по 4 пакета);
- самые короткие пакеты (до 256 байт: подтверждения TCP, DNS, пинг) идут сразу по двум маршрутам: какой дойдёт первым, тот и считается, второй WireGuard отбрасывает как повтор;
- пакеты, пришедшие по разным маршрутам не по порядку, выстраиваются по номеру пакета WireGuard (он виден без расшифровки), прежде чем их увидит WireGuard: пакет, пришедший раньше, ждёт предыдущие не дольше 10 мс (`core/engine/reorder.go`, у сервера — та же копия). Опоздавшие и повторы проходят сразу;
- новый маршрут начинает со скорости, на которой недавно держались маршруты через тот же TURN-сервер, и до первых признаков перегрузки разгоняется быстрее (+8 % за 100 мс, потом +2 %);
- с сервером без отчётов (стандартный, прежний TurnVK) клиент отправляет как раньше, без управления скоростью; прежние клиенты TurnVK получают управление по отчётам в PING раз в 2 с.

Отказ маршрутов и плохие TURN-серверы VK:

- каждый пинг маршрута (раз в 2 с) — ещё и проверка: маршрут, не ответивший за 2 с, перестаёт получать трафик, пока не ответит (раньше — через 10 с молчания). Маршрут, молчащий 6 с, пока другие отвечают, заменяется новым (раньше — через 25 с), а замена маршрута, проработавшего больше минуты, открывается сразу, без паузы — если только не упало сразу много маршрутов (смена сети, перезапуск сервера): тогда новые выделения растягиваются во времени, как раньше;
- сервер TurnVK перестаёт слать в маршрут, если клиент не подтвердил отправленное за 0,75 с (клиент TurnVK подтверждает каждый пакет отчётом FEEDBACK), и снова шлёт, как только по маршруту что-то пришло;
- VK выдаёт на звонок несколько TURN-серверов, и они неравноценны: в замере с тестового сервера через один терялось 2–14 % пакетов сервера, через другой — 0–1 %, и первый пропускал в 3–5 раз меньше. Клиент считает потери по каждому TURN-серверу (окна по 10 с, не меньше 300 пакетов) и, если один заметно хуже лучшего (потери больше 3 % и больше чем вдвое), новые маршруты открывает на лучшем, а с плохого переводит по одному маршруту в 10 с; два остаются на нём, чтобы его продолжать мерить. Когда потери у серверов равны, ничего не меняется (`core/engine/relays.go`);
- закрывая маршрут, клиент освобождает его выделение TURN и дожидается ответа VK (при устаревшем nonce — повторяет с новым), а при отключении ждёт этого до 3 с: выделение, которое VK продолжает считать, при быстром перезапуске упирается в лимит (ошибка 486) и уводит маршруты на нового гостя VK, а это может стоить капчи. Библиотека pion отправляет освобождение один раз без ожидания. На тестовом сервере VK подтвердил освобождение всех 16 выделений в каждом прогоне; ошибки 486 в замерах появлялись только после проверок с заблокированным TURN-сервером, когда освобождение до VK не доходило. Не освобождённые выделения клиент пишет в журнал;
- если новый маршрут через TURN-сервер не открылся, или все маршруты через него разом замолчали, новые маршруты минуту обходят этот сервер; маршрут, который не открылся, пробует следующий сервер. Раньше каждый маршрут всегда шёл на один и тот же сервер, и если тот переставал отвечать, половина маршрутов не восстанавливалась до перезапуска.

Файлы `core/session/pace.go` и `core/engine/reorder.go` общие с сервером (`internal/wdtt/pace.go` и `internal/wdtt/reorder.go` в wdtt-router): копии должны совпадать.

Упорядочивание и быстрый старт 15.11 не дали заметной разницы в замерах: в тот час домашняя сеть была перегружена (замеры на 32 маршрутах — 12–24 Мбит/с у обеих версий), и разница тонула в шуме. Хуже ни в одном прогоне не стало.

Проверка на Android 14 (эмулятор, настоящий движок, 32 маршрута, 15.11): подключение и все экраны работают; пинг сервера через туннель — 53–67 мс (в среднем 57) без потерь; отдача — около 20 Мбит/с, загрузка — 14–20 Мбит/с. Отдача на телефоне в 5–8 раз быстрее, чем у консольного клиента, — значит, медленная отдача консольного клиента — особенность его встроенного стека TCP (gVisor), а не туннеля.

Отказ TURN-сервера VK посреди загрузки 150 МБ (16 маршрутов, тестовый сервер, 15.11; сервер VK перестаёт пропускать пакеты на 30-й секунде):

| | прежний клиент | новый клиент |
| --- | --- | --- |
| сервер отвечает ошибкой | остаётся 8 маршрутов из 16 до конца; 9–11 Мбит/с в среднем | 16 из 16 через несколько секунд, все через исправный сервер; 14–20 Мбит/с |
| сервер молча перестаёт пропускать | 8 рабочих маршрутов из 16 до конца | замолчавшие заменены через 7 с, 16 из 16 через 9–12 с |

При молчаливом отказе загрузка у нового клиента на 5–6 с останавливается совсем (TCP отправителя ждёт повторов после потерь первых долей секунды), потом идёт на полной скорости; у прежнего — около 10 с на 2–8 Мбит/с, а дальше на половине маршрутов. За 20 с после отказа новый клиент получил примерно в 1,6 раза больше данных.

Стандартный сервер и стандартные клиенты работают как раньше.

## Приложение Android

- Вкладки, как в приложении Windows: «Главная», «Серверы», «Настройки», «Журнал».
- Несколько серверов: ссылки `wdtt://` сохраняются под именами, открытая извне ссылка предлагается к сохранению; ссылкой можно поделиться. Имя, которое приложение придумало само («Сервер адрес»), меняется вместе со ссылкой.
- Главный экран: кнопка подключения, время в сети, скорость загрузки и отдачи с графиком за минуту, пинг до сервера, число маршрутов, адрес в VPN, трафик, состояние каждого маршрута, протокол.
- Плитка в шторке быстрых настроек, кнопка «Отключить» в уведомлении.
- Приложения в обход VPN (банки и т. п.); приложения VK идут в обход всегда.
- Подключение при включении телефона; «Постоянная VPN» и «Блокировать подключения без VPN» Android работают с TurnVK.
- Проверки в настройках: экономия заряда (может усыплять VPN) и уведомления (нужны для проверки VK).
- Журнал: копировать, отправить, очистить; кнопка «Собрать отчёт» (см. «Отчёт для разработчика»).
- По умолчанию 32 маршрута (около 45 Мбит/с); можно от 8 до 64.

## Приложение Windows

`TurnVK.exe` — окно с теми же вкладками и настройками, что на Android, и VPN для всего компьютера через Wintun (`wintun.dll` встроен и кладётся рядом с программой при запуске).

- При запуске просит права администратора (окно UAC): без них Windows не даёт создать сетевой адаптер. Адаптер «TurnVK» существует только на время подключения.
- Весь IPv4 идёт в туннель двумя маршрутами `/1`, DNS — через сервер. IPv6 туннель не везёт: адаптер забирает и его, чтобы он не шёл мимо VPN.
- Собственные соединения TurnVK (VK, TURN, DNS для имён VK) привязаны к сети, через которую Windows ходит в интернет (`IP_UNICAST_IF`); при смене сети TurnVK переподключается.
- Если работает другой VPN (v2RayTun, OpenVPN, WireGuard…), приложение предупреждает: его более узкие маршруты забирают большую часть трафика, а DNS уходит в TurnVK, и программы (например, Discord) ломаются. Подключение при запуске в этом случае не выполняется.
- `TurnVK.exe wdtt://…` — добавить (или выбрать) сервер и подключиться.
- Настройки — `%APPDATA%\TurnVK\settings.json`, журнал — `%LOCALAPPDATA%\TurnVK\turnvk.log`. Номер устройства и гостевые токены VK общие с консольным клиентом.
- Нужен Microsoft Edge WebView2 Runtime (в Windows 10/11 обычно уже есть).

## Отчёт для разработчика

На вкладке «Журнал» обоих приложений кнопка «Собрать отчёт» собирает за несколько секунд текст для разработчика и копирует его (на Windows он ещё сохраняется в `%LOCALAPPDATA%\TurnVK\report-….txt`, на Android им можно поделиться). В отчёте:

- система: версия Windows или Android, устройство; на Windows — адаптеры, их адреса и DNS, маршруты, которые забирают интернет, другой VPN и сеть, к которой привязаны маршруты TurnVK; на Android — сети и их тип;
- настройки и сервер (адрес, порты, число звонков VK, есть ли ключ сервера — без пароля и звонков);
- подключение: маршруты по серверам TURN с пингом и потерями, ответил ли сервер на рукопожатие WireGuard и когда, трафик через туннель каждые 10 секунд за последние 15 минут;
- проверки: DNS и API VK; на Windows при подключении — ещё DNS туннеля, доступ в интернет, внешний адрес (совпадает ли с сервером), Discord и YouTube через VPN. На Android приложение само не ходит через свой VPN, поэтому проверки через туннель там не делаются;
- последние 400 строк журнала.

Ссылки `wdtt://`, звонки VK, токены и длинные ключи заменяются на `<hidden>`. В журнал движок теперь пишет первое рукопожатие WireGuard (или что сервер не ответил за 15 секунд) и раз в минуту — трафик, число маршрутов и возраст рукопожатия.

## Консольный клиент (Windows, Linux, macOS)

```bash
turnvk -link "wdtt://…"                 # SOCKS5-прокси на 127.0.0.1:1080
turnvk -link "wdtt://…" -test           # проверить туннель (IP выхода, DNS) и выйти
turnvk -link "wdtt://…" -download URL   # замер скорости
turnvk -link "wdtt://…" -download URL -stats -ping 10.66.67.1   # скорость, потери и пинг по секундам
turnvk -link "wdtt://…" -upload 20 -stats                       # отдача 20 МБ
```

Встроенный стек TCP консольного клиента (gVisor) настроен под VK TURN: CUBIC и буферы по 4 МБ (до 16 МБ) вместо Reno и 1 МБ. Отдача с 16 маршрутами на тестовом сервере: 2–8 Мбит/с с настройками gVisor, 11–12 с CUBIC и буфером 1 МБ, 13–17 с буферами 4 МБ. Главное — буферы: отправитель держит в пути не больше буфера, а при пачках потерь VK большая часть ждёт повтора. Для сравнений: `TURNVK_TCP=off` (настройки gVisor) или, например, `TURNVK_TCP=cc=reno,buf=1M`; `TURNVK_SCORE=off` — без оценки TURN-серверов.

Замер по сценариям (простой туннель, загрузка с 16 и 32 маршрутами, короткая загрузка 5 МБ, отдача, 2 % потерь на сервере, перезапуск сервера) — `scripts/bench.sh`. Скорость он меряет до `scripts/bench-endpoint` — маленького сервера, который запускается на тестовом сервере на адресе туннеля: публичные замеры (Cloudflare) после десятков прогонов начинают отказывать и добавляют шум интернета. На сервере с fail2ban частые подключения по SSH (сценарии с потерями и перезапуском) могут привести к временному бану адреса. С `BENCH_LOCAL=1` скрипт запускается на самом тестовом сервере (клиент оттуда тоже идёт через TURN VK): замеры не зависят от домашней сети, а сценарии с потерями и перезапуском не открывают SSH. Он пишет строку на сценарий в `bench-results.txt`, а полные журналы клиента — в `bench-results-logs/`. Учётные данные VK сохраняются, поэтому повторные прогоны в пределах часа не обращаются к VK.

Флаги: `-sessions` (по умолчанию 16), `-stats` (раз в секунду: скорость, маршруты, их задержка и потери; в конце — строка `ROUTE` на каждый маршрут: TURN-сервер, задержка, потери), `-ping адрес` и `-pings N` (пинг через туннель во время проверки), `-obfs audio|video`, `-device-id`, `-turn host:port`, `-dns`. Если VK просит капчу, на Windows открывается окно с ней (WebView2). Гостевые токены VK хранятся в `%LOCALAPPDATA%\turnvk\vk-guests.json` (Linux: `~/.cache/turnvk/`), так что повторный запуск капчу не вызывает.

| Пакет | Что делает |
| --- | --- |
| `core/link` | разбор ссылок `wdtt://` |
| `core/wrap` | RTP-маскировка (формат сервера WDTT) |
| `core/vkcreds` | учётные данные TURN из звонка VK, капча через интерфейс `CaptchaSolver`, кэш гостевых токенов |
| `core/session` | один маршрут: TURN → маскировка → прямой протокол (`direct.go`) или DTLS → GETCONF |
| `core/engine` | пул сессий, WireGuard в процессе, переподключение, сторож |

| `mobile` | API для Android (gomobile) |
| `core/winvpn` | VPN на Windows: адаптер Wintun, маршруты, DNS, привязка своих сокетов к сети, поиск другого VPN |
| `core/diag` | отчёт для разработчика: текст, сокрытие секретов, сетевые проверки |
| `core/webcaptcha` | окно капчи VK на Windows (WebView2) |
| `cmd/turnvk` | консольный клиент |
| `cmd/turnvkw` | приложение Windows: окно (WebView2, `ui.html`), настройки, значок |

## Дальше

- Windows: служба для автозапуска (без окна UAC при каждом запуске), значок в области уведомлений, блокировка трафика мимо VPN.
- Android: подпись релизов, сканирование QR-кода со ссылкой.
- Протокол: число маршрутов по нагрузке; FEC для сетей с большими потерями; медленное хеширование пароля для внешнего слоя. Запасные маршруты (открытые заранее) отложены: каждый требует учётных данных VK сверх нынешних, то есть нового гостя и, возможно, капчи; вместо них — быстрая замена (см. «Скорость и задержка»).
- Справедливая очередь по соединениям на сервере (звонок не дёргается во время большой загрузки): отдать очередь ядру (`fq_codel` на `wdtt1`) нельзя — библиотека WireGuard при заполнении своих очередей отбрасывает пакеты, а не придерживает чтение. Нужен свой планировщик перед шифрованием; отложено, пока не будет способа измерить пользу.
- Редкие выбросы пинга до 110–200 мс в замерах — это домашняя сеть: в те же моменты так же вырастает задержка до TURN-сервера VK напрямую, без туннеля.

## Капча VK: как её стало меньше

VK спрашивает капчу только на первых трёх шагах входа в звонок (анонимный токен, превью звонка, токен звонка). Эти токены живут сутки, а учётные данные TURN, которые из них получаются, — 8 часов (срок зашит в имени пользователя TURN). Поэтому:

- токены звонка сохраняются (`vk-guests.json`) и используются повторно: новые учётные данные TURN берутся одними шагами calls.okcdn.ru, где капчи нет, в том числе после перезапуска приложения;
- если VK перестал принимать сохранённый токен, клиент один раз входит заново (и только тогда может понадобиться капча);
- пока прежние учётные данные TURN действуют, новые запрашиваются в фоне: неотвеченная капча не мешает переподключениям, а пропущенная не спрашивается снова 15 минут;
- на Android, когда капча всё же нужна, приходит уведомление «Нужна проверка VK»; оно исчезает, как только проверка пройдена, отменена или больше не нужна.
